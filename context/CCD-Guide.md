Conversion-Centered Design (CCD) Architecture Guidelines
1. System Context & AI Orchestration Rules
This document serves as the core architectural reference for generating UI/UX components and frontend code. 
The primary objective of all generated code must be to guide the visitor toward a single, measurable action (the conversion).
When generating code, the AI must:Prioritize user actions and conversions over general aesthetics or complex technical features.Enforce content and accessibility rules before code generation, validating UI components against these core CCD principles.Prevent the introduction of extraneous navigation or dashboard elements that distract from the main Call-to-Action (CTA).

3. Core UI/UX DirectivesWhen creating components, apply the following Conversion-Centered Design principles:Absolute Focus: Remove main website navigation bars, footer links, and secondary pathways that could lead the user away from the intended conversion goal.Encapsulation: Wrap critical CTAs and forms in distinct visual boundaries, utilizing high-contrast colors and liberal whitespace to draw the eye.Directional Cues: Utilize visual elements (e.g., arrows, linear pathways, or photography lines of sight) to subconsciously point the user toward the conversion element.Simplified Lead Capture: If forms are required, utilize dynamic, multi-step forms rather than single, long questionnaires to reduce user friction.
4. Technical Implementation & Performance StandardsSite speed and technical structure directly impact conversion rates. All generated frontend code must conform to:Mobile-First Speed Optimization: Ensure the headline, unique value proposition, and primary CTA are placed "above the fold" and load instantly without requiring the user to scroll.Asset Minification: Minify all CSS, HTML, and JavaScript, and defer the loading of non-critical, below-the-fold scripts.Image Rendering: Use modern image formats such as WebP and implement lazy-loading for assets that appear below the fold.
5. Third-Party Integrations (Fundraising Specific)Secure Pitch Deck Embedding: Do not generate standard <a href="...pdf" download> tags for the pitch deck. Instead, implement embeds or secure gateway links using document analytics platforms (like DocSend) to maintain intellectual property control and capture investor engagement metrics.

6. Hero Manifesto & Section Height Rules

- Hero = Full-Screen Manifesto: The hero section (headline, subcopy, primary CTA, and supporting visual) must be designed to fill at least one full viewport height on standard laptop and mobile breakpoints. No "short" hero strips.
- Manifesto-Level Copy Density: The hero must contain enough persuasive copy to tell a complete, conviction-building story on its own (problem, promise, proof cue, and CTA), not just a slogan and button.
- Single Dominant CTA Above the Fold: There must be one primary CTA in the hero, visually dominant and immediately discoverable without scrolling.
- Visual Weight & Hierarchy: Typography, spacing, background imagery/gradients, and contrast should be tuned so that the hero feels like the heaviest, most important band on the page.
- Viewport-Locked Sections: All primary sections (hero, traction, offer, team, FAQ, etc.) should be designed such that each feels like its own "screen" – target 80–120% of viewport height with generous vertical padding, instead of thin bands.
- Scroll Rhythm: When scrolling, the visitor should land in clearly separated narrative blocks (one core idea per screen). Avoid stacking multiple unrelated subsections in a single viewport.
- Implementation Constraint for Generators: When generating layouts, default section containers to min-height: 100vh (or a responsive equivalent using CSS clamp) for primary narrative sections, unless explicitly overridden.
